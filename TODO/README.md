## 一、这一轮新做出来并跑通的东西

### 1. World Port Index 港口点位 → 打通「在港 / 锚泊」判定

数据：`world_port_index.zip`（NGA WPI，2017 版）→ `data/ports/WPI.dbf` → 导入 `ports` 表，**3669 个港口全部导入，0 条丢弃**。

- 解析器不依赖 pyshp/geopandas，直接按 dBase 定长记录切字段：`scripts/load_wpi.py`
- 原始字段 `INDEX_NO / PORT_NAME / COUNTRY / LATITUDE / LONGITUDE / HARBORSIZE / HARBORTYPE` 全部保留，
  另存 `harbor_size_code`（V/S/M/L）供逻辑判断，中文标签只用于展示
- 查询：`backend/app/services/ports.py`，内存 0.5° 网格分桶，**单次查询约 0.04 ms**，2000 次查询 0.01 秒

**在港半径按港口规模分档**，不是拍一个固定值：

| WPI 规模 | 在港半径 | 理由 |
|---|---|---|
| L 大港 | 12 km | 汉堡沿易北河、鹿特丹沿新水道，泊位铺开十几公里 |
| M 中等 | 8 km | 阿伯丁这类 |
| S 小港 | 4 km | |
| V 很小 | 3 km | 渔码头只有几百米 |
| 未知 | 5 km | 兜底 |

时间线的静止段现在分成 `port_stay`（在港）与 `anchorage_candidate`（锚泊/漂航），
证据里带最近港口名、国家、规模、距离、以及「为什么这么判」的一句话。

### 2. Ocean Engine（按需环境提取 + 两层缓存）

数据源：`cmems_mod_glo_phy_anfc_0.083deg_PT1H-m`
（全球海洋物理分析预报，1/12°，**逐时平均**，含 analysis + 10 天预报）

取表层（0–1 m）：`thetao`→`sst_c`、`uo`/`vo`→`u_m_s`/`v_m_s`、`zos`→`ssh_m`

**这里踩了一个坑，值得记下来**：最先试的 `..._P1D-m` 数据集里**没有** `thetao`/`uo`/`vo`，
只有海冰、混合层、海底温盐这类 2D 场。真正带三维物理量的是逐时数据集，
而且要带 `_P1H-m` 后缀、用深度区间（0–1 m）而不是精确值
（`0.494025` 会被浮点精度判成越界）。

三层结构：
- **L1** `ocean_features`：每个轨迹点匹配到的环境值，按 `(mmsi, ts)` 幂等缓存，TTL 30 天
- **L2** `ocean_cache_tiles` + `data/ocean_cache/*.nc`：1°×1° 的**整日**切片，TTL 6 小时
- **L3** 派生特征（锋面距离、SST 梯度、异常）：**尚未实现**

采样规则：按 30 分钟抽稀，单次最多 240 点，单次最多新建 4 个瓦片（每个约 10–30 秒）。

实测结果：

| 场景 | 结果 |
|---|---|
| 爱琴海（37.5°N 23.4°E） | SST 22.33 °C，流速 ~0.08 m/s，滞后 0.2 h，6/6 点可用 |
| 佛罗里达外海（25.8°N 80.1°W） | SST 27.76 °C，滞后 0.25 h，6/6 点可用 |
| 荷兰内陆水道（53.0°N 5.7°E） | 全部 `land_mask` —— 全球海洋模式把这些内河/潟湖判成陆地，**这是正确行为** |
| 西雅图 Lake Union | 全部 `land_mask`，同上 |

时效：NRT 产品本身有约半天内的滞后，每个点都记 `source_time` 与 `lag_hours`，
超过 36 小时直接判 `out_of_range`，**绝不把过期 SST 当成此刻的 SST**。

### 3. 异步任务 worker（`analysis_jobs` 真正跑起来了）

- `backend/app/services/jobs.py`：入队 / 抢占 / 进度 / 完成 / 结果快照 / 卡死回收
- `analytics/job_worker.py`：常驻轮询（3 秒），`run.py` 自动作为第 4 个子进程拉起，日志 `logs/worker.log`
- 同一参数重复提交自动去重，用户连点三次不会发三次远程请求
- 实测：提交 → 抢占 → 完成 → 结果落 `analysis_results`，冷瓦片 20 秒、热瓦片 4 秒

### 4. 接口与工具

新增接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/analysis/ocean/capabilities` | 环境引擎自检：依赖、凭证、产品、**明确没做什么** |

—— 先读缓存；没缓存就提交任务并最多等 45 秒；等不到**如实返回 job_id，绝不编造数值**。

### 5. 前端

行为时间线片段新增「在港 / 锚泊」小标签，甘特条对在港段加蓝边，
鼠标悬停显示最近港口名与距离。`sub_label` 也进了地图定位的 tooltip。

### 6. 测试

`tests/test_ports_ocean_jobs.py` 新增 22 个用例，合计 **58 个全绿**。重点覆盖：

- 在港半径必须按规模单调递增（大港半径 > 中港 > 小港 > 小码头）
- 港口表为空时必须降级为「锚泊候选」，不能谎称在港

- 瓦片分桶必须按 1° × UTC 自然日

## 一·补、v0.4 这一轮补上的三件事

### A. 海浪（CMEMS WAV）—— 风浪里「浪」这一半解决了

数据集：`cmems_mod_glo_wav_anfc_0.083deg_PT3H-i`（1/12°，3 小时，分析 + 预报）

| 变量 | 列名 | 含义 |
|---|---|---|
| `VHM0` | `wave_height_m` | 有效波高（谱矩 0 阶） |
| `VMDR` | `wave_dir_deg` | 波向（来向，正北顺时针） |
| `VTM02` | `wave_period_s` | 平均周期（谱矩 0/2 阶） |

**关键点**：海浪是 2D 场，`subset()` 里**不能传 depth**，传了会被服务端拒绝。
凭证沿用同一套 Copernicus 账号，不用新注册。

派生：`sea_state` 按道格拉斯海况表（0.1 / 0.5 / 1.25 / 2.5 / 4 / 6 / 9 / 14 m）查表。
**这是国际通用经验分档，纯查表，不是推断**，所以可以当标签用；`wave_height_m` 缺测时老实返回 `unknown`，
不会默认成「无浪」。

实测爱琴海：0.27–0.56 m（微浪~小浪），汉堡港内全部 `land_mask`。

### B. 叶绿素 —— 实时仍然没有，改成标注清楚的**气候态**

再确认一次：`cmems_mod_glo_bgc-bio_anfc_0.25deg_P1D-m` 请求 `chl` 直接报
`VariableDoesNotExistInTheDataset`（只暴露 `nppv` / `o2`）。这是产品本身没有，不是代码问题。

于是改用 `cmems_mod_glo_bgc_my_0.25deg_P1M-m`（历史逐月）做 **2019–2023 同月气候态**：

- 一个瓦片一次请求 60 个月（5 年 × 12 月），在像元上按月聚合，逐点取当月
- `chl_basis='climatology'`、`chl_ref='2019-2023'`、`lag_hours=null`
- **顶层 `source_time` / `lag_hours` 只跟随实时产品**：气候态写进去会把「2019–2023 年 10 月平均」
  伪装成「今天 03 时的值」，所以代码里显式拦掉了
- 界面上叶绿素卡带黄色「气候态」徽标，底部固定一句「不是当前浓度」

实测爱琴海 10 月：0.085–0.095 mg/m³。

**为什么不做 `I://Diff` 那套 0.1° 全量数据**：`parts/bgc` 至今 0 个文件（`parts/physics` 有 2320 个），
补全要 3832 个任务；而气候态只需要按需取 1 个瓦片、十几秒。等真要做「历史作业—环境」配对分析时再补。

### C. 环境面板 + 证据卡界面

界面原来只有 API 和智能体能拿环境数据，现在侧栏有了：

- **环境背景**：海温 / 流速 / 浪高三个指标卡 + 三条曲线，缺测**断线不插值**，
  一眼能看出「哪段没数据」；底部标「匹配 6/7 采样点、滞后中位 0.8h」
- **证据卡**：观测事实 / 统计推断 / 无法得知 三色分区 + 复核状态徽标 + 替代解释折叠

顺带修了两个「自相矛盾」：

1. **证据卡说「没有中断」，时间线却画着一段中断** —— 因为 `gap_cards` 只查 `ais_gap_events`，
   而时间线的缺口是即时算出来的。现在事件表为空时回退到时间线片段，
   并支持「窗口开头就是断档」这种情况（此时断点前没有报文，`lat/lon` 置空，
   绝不拿断点后的位置冒充断点前的，否则会得出「位置连续」的假结论）。
2. **同一 `(mmsi, ts)` 被多个产品写会互相清空** —— 原来 `_persist` 是整行 `INSERT OR REPLACE`，
   海浪写进去会把刚取的 SST 冲成 NULL。现在改成先读现有行、按产品负责的列合并，
   `quality_json` 逐产品记录 quality/basis/source_time/lag_hours。

还有一个隐蔽的坑：`_load_cached` 只判断「行存在」，于是后写的产品看到 physics 写的行
就以为全部命中缓存，**一个字都不抓**。现在按 `products` 字段 + 本产品列是否有值双重判断。

## 二、现在做不了的，以及卡在哪

### ① Vessel DNA 依然建不起来 —— 卡在数据时长（唯一真正的硬限制）

**现状**：`closed_trips = 0`。数据库时间跨度约 **2.5 小时**（2026-10-27 08:55 起）。

**原因**：航次基线要求同一艘船至少 3 个**已闭合**航次，每个航次需要一次真实的「出海—返港」，
近海渔船通常 1–3 天一个循环。

**结论**：现在跑 `compare_vessel_behavior` 只会返回 `insufficient_history`，这是**正确行为**。

**补齐条件**：采集器连续跑 **3–9 天**（30 天可建季节分层基线）。代码已就绪，数据一到自动通。
**这条不需要你做任何事，只要别关机器。**

### ② 实时叶绿素 / 硝酸盐 / 溶解氧仍然取不到 —— 卡在数据集本身

**现状**：`cmems_mod_glo_bgc-bio_anfc_0.25deg_P1D-m` 请求 `chl` 报
`VariableDoesNotExistInTheDataset`，只暴露 `nppv` 与 `o2`。**已经第二次实测确认。**

**已给的替代**：2019–2023 同月**气候态**（`bgc_clim`），标注 `chl_basis=climatology`，
`lag_hours=null`。它能回答「这个季节这片海通常多肥」，**不能**回答「今天多肥」。

**补齐条件**：等 Copernicus 给 BGC NRT 补上 chl（时间不定）；
或者接 `I://Diff` 那套 0.1° 历史数据（`parts/bgc` 还没开始，3832 个任务）。

### ③ 风已经接了，而且接了三个源 —— 但每个源都有自己的延迟，必须说清

原来的结论「CMEMS 物理产品没有风」是对的，但**CMEMS 有独立的风产品**：
`cmems_obs-wind_glo_phy_nrt_l4_0.125deg_PT1H`（卫星散射计 L4 融合，同一套凭证）。
实测它滞后约 2 天、覆盖从 2024-06-13 起。

问题在于：本系统采到的 AIS 数据只有最近几小时，**2 天的滞后等于什么都取不到**。
ERA5 更差，滞后 5 天。所以只接这两个，功能等于没接。于是最终接了三源：

| 产品 | 源 | 延迟 | 语义 | 用途 |
|---|---|---|---|---|
| `wind_gfs` | NOAA GFS 0.25°（NOMADS 子集） | **约 5 小时** | 分析场 + ≤3h 短时预报 | **默认**，唯一能覆盖「今天」 |
| `wind` | CMEMS 卫星散射计 L4 融合 | 约 2 天 | **观测** | 有观测时的最佳选择 |
| `wind_era5` | ERA5 再分析（CDS） | 约 5 天 | 再分析模式 | 历史回填 / 长时段研究 |

**为什么不走 ECMWF open data**：实测它不支持区域裁剪，一次要下全球场
（约 20 MB/起报，一天 80 MB），比 GFS 的区域子集（**一天 10 KB**）贵三个数量级。
GFS 用 `filter_gfs_0p25.pl` 只取 1°×1°，一天 8 次小请求共约 10 KB、14 秒。

**为什么每点都记 `wind_basis`**：三个源都叫「风」，数值能差 1–2 m/s。
不记来源，数据一旦混起来就再也分不清哪个是观测、哪个是模式。

派生字段：`beaufort_of()` 按蒲福风级表查表（13 级），`wind_dir_text()` 给八方位。
两者都是**纯查表**，不含推断，所以可以当标签用。

**风向约定是「来向」**：352° 表示北风（风从北边吹来），不是「吹向北」。

### ④ 环境偏好分析做不了 —— 缺对照样本，这是方法论问题不是数据问题

现在只能回答「这艘船**经历过**什么环境」，不能回答「这艘船**偏好**什么环境」。

要回答偏好必须构造「可选但未使用」的时空对照，并控制港口距离、可达性、季节、船舶差异。
否则必然得出「这艘船偏好 20 °C 海水」这类伪结论。**这是刻意不做的，不是漏掉的。**

### ⑤ 行为标签无法校准，`confidence` 只能是 null —— 卡在标注数据（按你的决定先不做）

按「先用速度阈值、做简单点」的决策，当前保持规则层：

- 标签由 `SOG` 阈值切分：`<0.5` 静止 / `0.5–4.5` 低速 / `≥4.5` 航行
- `fishing_candidate` 仍是速度 + 航迹形态的**规则打分**（`rule_score`），不是概率
- `gear_type` 恒为 `unknown`，不区分拖网/围网/延绳钓

**顺带修了一个真 bug**：`_build()` 里 `push()` 会重新计算 stats，把外部塞进
`evidence.rule_score` 的字段覆盖掉 —— 之前的候选段其实**没存下 rule_score**。
现在改成把已算好的 stats 传进 `push()`，并补了断言。

### ⑥ 中国近海基本没数据 —— 按你的决定，暂不补

AISStream 免费流覆盖重心在欧洲。当前数据库里点位最密的是荷兰内河（52°N 5°E）、
西雅图（49°N 123°W）、爱琴海（38°N 24°E）、迈阿密（26°N 80°W）。
**这是数据源问题，改代码解决不了。**

### ⑦ 仍在单机 SQLite

31 MB 库、23 万轨迹点，跑得动。按当前速率约 1 个月到千万级，到那时再迁 PostGIS
（`database/init_postgis.sql` 已写好）。

### ⑧ SAR 验证：明确不做

需要影像检索 + 目标检测 + 成像时间匹配 + 定位误差处理，成本远高于当前收益。

## 四、一句话总结

**「这艘船某段时间做了什么、在港还是在海上、处在什么水温海流浪高里」这条链，
现在能从 API、智能体、界面三个入口拿到，而且每个结论都带着证据、时效和不确定性。**

**「这艘船某段时间做了什么、在港还是在海上、处在什么水温/海流/浪高/风里」整条链已经打通**，
风速再也不是缺项。

真正卡住的只剩一件事：**数据时长**（要再跑几天才有闭合航次）。
外部数据源还缺一样：实时叶绿素（给了气候态替代）。
刻意不做的两样：环境偏好、概率校准。
